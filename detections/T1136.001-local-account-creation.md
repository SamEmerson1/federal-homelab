## Hypothesis

An adversary who has gained execution on a workstation frequently creates a local account to
survive credential resets and to hold access independent of the compromised user. Windows records
local account creation as Security event 4720 on the machine where it happened. In a managed
environment, accounts are provisioned in the domain, not in a workstation's local SAM — a 4720 on a
member host is either a technician working outside process or an adversary, and both are worth a
look.

The follow-on action, adding that account to a privileged local group, generates 4732. Correlating
the two in a short window separates routine account creation from privilege establishment.

A 4720 on DC01 records a *domain* account, which is T1136.002 and out of scope for this detection.

## Detection logic

Written against XML-rendered Security events (`renderXml = true`, source `XmlWinEventLog:Security`),
whose field names are the `EventData` names in the table below. Field names are confirmed against
indexed data before validation.

```spl
index=lab_win source="XmlWinEventLog:Security" EventCode=4720 host!="DC01"
| rename TargetUserName as new_account, TargetSid as new_account_sid, SubjectUserName as created_by
| search NOT created_by IN ("*$", "SYSTEM")
| table _time, host, new_account, new_account_sid, created_by, SubjectDomainName
| sort - _time
```

Correlated version — creation followed by membership in a privileged local group within 10 minutes.
The two events share no account name: in 4732, `TargetUserName` is the **group**, and the account
added appears only as `MemberSid`. The join is therefore on SID, 4720 `TargetSid` to 4732 `MemberSid`.

`net user /add` also places every new account in the local Users group, which raises its own 4732.
Restricting the 4732 side to privileged built-in groups by well-known SID keeps that from matching.

```spl
index=lab_win source="XmlWinEventLog:Security" host!="DC01"
    (EventCode=4720 OR (EventCode=4732 TargetSid IN ("S-1-5-32-544", "S-1-5-32-551", "S-1-5-32-555", "S-1-5-32-580")))
| eval account_sid = if(EventCode=4720, TargetSid, MemberSid)
| eval created   = if(EventCode=4720, _time, null()),
       added      = if(EventCode=4732, _time, null()),
       new_account = if(EventCode=4720, TargetUserName, null()),
       group      = if(EventCode=4732, TargetUserName, null())
| stats min(created) as created, min(added) as added, values(new_account) as new_account,
        values(group) as group, values(SubjectUserName) as actor, values(host) as host by account_sid
| where isnotnull(created) AND isnotnull(added) AND added >= created AND added - created <= 600
| eval seconds_to_privilege = added - created
| convert ctime(created) ctime(added)
| table host, new_account, account_sid, group, actor, created, added, seconds_to_privilege
```

| SID | Group |
|---|---|
| `S-1-5-32-544` | Administrators |
| `S-1-5-32-551` | Backup Operators |
| `S-1-5-32-555` | Remote Desktop Users |
| `S-1-5-32-580` | Remote Management Users |

## Field reference

| Field | Source | Meaning |
|---|---|---|
| `EventCode=4720` | Security log | A user account was created |
| `EventCode=4732` | Security log | A member was added to a security-enabled local group |
| `TargetUserName` | 4720 | The account that was created |
| `TargetSid` | 4720 | SID of the account that was created |
| `SubjectUserName` | 4720, 4732 | The account that performed the action |
| `SubjectDomainName` | 4720 | Domain or local machine context of the creator |
| `TargetUserName` | 4732 | The **group** the member was added to — not the account |
| `TargetSid` | 4732 | SID of the group |
| `MemberSid` | 4732 | SID of the account added. `MemberName` is typically `-` for local accounts |

## False positives

| Scenario | Likelihood | Tuning |
|---|---|---|
| Helpdesk creating a local admin during a break-fix | Medium in production, low in this lab | Allowlist known technician accounts; alert on the correlation rather than bare 4720 |
| Software installers creating service accounts | Medium | Allowlist specific account name patterns after observing a baseline |
| Your own lab setup work | High | Filter your build window by time, or baseline after the lab is built |

## Response guidance

1. Identify the creating account and whether it should have that capability at all.
2. Check for a preceding 4688 or Sysmon EID 1 showing `net user` or `New-LocalUser`, and look at the parent process.
3. Determine whether 4732 followed — group membership turns this from suspicious into urgent.
4. Check whether the new account has logged on (4624) and from where.
5. If unexplained: disable the account, preserve the host, and pivot to the originating process tree.

## Gaps

- Domain account creation (T1136.002) is out of scope: it produces 4720 on DC01, not on the member host, and needs its own detection with DC01 forwarding.
- The correlated search covers four privileged built-in groups by SID. Membership in a custom or domain group that carries local admin rights through Group Policy is not matched.
- An adversary using an existing dormant account creates no 4720 at all. Pair this with a dormant-account-reactivation detection for real coverage.
- Local account creation with auditing disabled generates nothing — which is why the STIG audit-policy settings and a detection for 1102 (log cleared) matter alongside this.
