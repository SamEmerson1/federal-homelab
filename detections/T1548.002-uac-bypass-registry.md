## Hypothesis

Several auto-elevating Windows binaries launch a helper program by reading a path from a per-user
registry key, for example `HKCU\Software\Classes\mscfile\shell\open\command`. Because the key lives
in the user's hive, a normal user can write to it, and the auto-elevating binary — Event Viewer
(`eventvwr.exe`) in this case — then runs the planted command at high integrity without a UAC
prompt. Writing to one of these handler keys is the signature of the technique.

Sysmon records registry value writes as event 13 (SetValue) and key/value deletes as event 12. The
detection watches for a write to a `shell\open\command` key under the handler names these bypasses
use.

## Detection logic

```spl
index=lab_sysmon source="XmlWinEventLog:Microsoft-Windows-Sysmon/Operational"
    (EventCode=12 OR EventCode=13) TargetObject="*\\shell\\open\\command*"
    (TargetObject="*ms-settings*" OR TargetObject="*mscfile*" OR TargetObject="*exefile*" OR TargetObject="*\\Folder\\*")
| table _time host User Image EventType TargetObject Details
```

`Details` holds the value written — the command the auto-elevating binary would run. `Image` is the
process that wrote the key, which is the more suspicious indicator: a shell or script interpreter
writing a handler key is not normal.

## Field reference

| Field | Source | Meaning |
|---|---|---|
| `EventCode=13` | Sysmon | Registry value set |
| `EventCode=12` | Sysmon | Registry key/value created or deleted |
| `TargetObject` | Sysmon | Full registry path written |
| `Details` | Sysmon | The value written (the planted command) |
| `Image` | Sysmon | The process that made the change |
| `EventType` | Sysmon | `SetValue`, `CreateKey`, `DeleteValue` |

**Note on elevation.** This detection confirms the *registry write*, which is the technique's
signature, not that a process ultimately ran elevated. WS01's UAC policy prompts on the secure
desktop for every elevation (`ConsentPromptBehaviorAdmin=2`), and Defender removed the planted value
within seconds, so on this host the bypass is unlikely to have completed. Detecting the write is the
point: it fires whether or not the elevation succeeds.

## False positives

| Scenario | Likelihood | Tuning |
|---|---|---|
| A legitimate installer registering a file-type handler | Low–medium | Allowlist by `Image` (the installer) and by the specific handler |
| Software writing `HKCU` class registrations | Low | Baseline which processes legitimately write these keys |

## Response guidance

1. Read `Details` — the command that was planted.
2. Identify `Image` — which process wrote the key. A shell or script interpreter is a strong signal.
3. Check for the auto-elevating binary (`eventvwr.exe`, `fodhelper.exe`, `computerdefaults.exe`)
   launching shortly after, and its child processes' integrity level.
4. If unexplained: capture the key contents, remove the planted value, and pivot to the writing
   process.

## Gaps

- Only the handler families in the search are covered (`ms-settings`, `mscfile`, `exefile`,
  `Folder`). Other UAC-bypass variants use different keys, different auto-elevating binaries, or no
  registry write at all (for example directory-mocking or token-manipulation methods) and would not
  match.
- The detection sees the write, not the outcome. Pair it with a rule for a high-integrity child of
  an auto-elevating binary to catch a successful bypass.
